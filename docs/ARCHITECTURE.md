# Архитектура HelpDesk

Этот документ — введение для разработчика, который умеет писать PHP, HTML+CSS
и JavaScript по отдельности, но никогда не работал с Laravel, Vue или
Inertia.js. Цель — дать достаточно понимания, чтобы уверенно ориентироваться
в проекте: что где лежит, зачем нужен каждый слой, и как они связаны друг с
другом.

Остальные документы в этой папке:
- [REQUEST_LIFECYCLE.md](REQUEST_LIFECYCLE.md) — подробный разбор пути одного
  запроса от браузера до готовой страницы, с примерами кода.
- [HOWTO.md](HOWTO.md) — практическое руководство: что где менять, что
  запускать, как деплоить, куда смотреть при поломке.
- [API.md](API.md) — справочник по всем HTTP-эндпоинтам системы (веб + JSON +
  мобильное приложение).

## 1. Что это за приложение

HelpDesk — система управления заявками техподдержки интернет-провайдера.
Операторы принимают заявки от абонентов, назначают бригады монтажников,
отслеживают выполнение. Бригадиры и монтажники работают через мобильное
приложение (Android) или мобильную веб-версию (PWA на `app.vega8.ru`).
Уведомления уходят в Telegram, корпоративный мессенджер Max и на email.

Это **один Laravel-проект**, который отвечает сразу за три вещи:
1. Основной веб-интерфейс (тот, что открывается на `vega8.ru`) — им пользуются
   операторы, бригадиры, руководство, бухгалтерия и т.д. за компьютером.
2. JSON REST API для Android-приложения и мобильной PWA (`/api/*`).
3. Фоновые задачи: рассылки, синхронизация, статистика (см. раздел 6).

Никакого отдельного "бэкенд-сервера" и "фронтенд-сервера" нет — это один и
тот же PHP-процесс, обслуживающий и HTML-страницы, и JSON-ответы, в
зависимости от того, какой URL и какие заголовки пришли в запросе.

## 3. Технологии проекта — и с чем они схожи

### 3.1 Laravel (PHP-фреймворк)

Laravel — это структура для PHP-приложения: роутинг, ORM для базы данных,
шаблоны, валидация, очереди задач, планировщик — всё "из коробки", вместо
того чтобы писать это самому на чистом PHP. Если раньше вы писали
`if ($_GET['page'] === 'tickets') { ... }` и руками собирали SQL-запросы —
Laravel берёт всё это на себя декларативно.

Аналогии с чистым PHP:
| Чистый PHP | Laravel |
|---|---|
| `$_GET`, `$_POST` | объект `Illuminate\Http\Request $request` |
| `mysqli_query("SELECT ...")` | Eloquent ORM: `Ticket::where(...)->get()` |
| `include 'header.php'` | Blade-шаблоны (`@include`), но в этом проекте почти не используются — см. ниже |
| руками парсить URL | `routes/web.php` — декларативная таблица "URL → метод контроллера" |
| `session_start()` + `$_SESSION` | тоже есть, но обычно не нужно трогать руками — сессии/куки обрабатываются middleware автоматически |

### 3.2 Eloquent ORM — как работает база данных

Вместо SQL-запросов вы работаете с PHP-классами-моделями
(`app/Models/Ticket.php`, `app/Models/Address.php` и т.д.), каждый
представляет одну таблицу БД. Например:

```php
// SQL: SELECT * FROM tickets WHERE status_id = 1 ORDER BY created_at DESC
Ticket::where('status_id', 1)->orderByDesc('created_at')->get();

// SQL: INSERT INTO addresses (...) VALUES (...)
Address::create(['city' => 'Донецк', 'street' => 'ул. Ленина', ...]);

// связи между таблицами объявлены в самой модели и вызываются как свойства:
$ticket->address->city;       // JOIN на addresses через address_id
$ticket->comments;             // все TicketComment с этим ticket_id
```

Схема таблиц не пишется руками в БД — она описана как последовательность
**миграций** в `database/migrations/*.php`. Миграция — это PHP-класс с
методом `up()` (что создать/изменить) и `down()` (как откатить). Чтобы
добавить новое поле в таблицу — создаётся новая миграция, а не правится
старая (см. [HOWTO.md](HOWTO.md)).

### 3.3 Vue 3 — фронтенд-компоненты

Vue — это способ описывать кусок интерфейса как самодостаточный компонент:
HTML-разметка + JS-логика + (опционально) стили в одном `.vue`-файле,
который "живёт" и сам перерисовывается, когда меняются его данные —
не нужно руками дёргать `document.querySelector` и менять DOM вручную.

Пример структуры файла (Composition API — тот стиль, который используется
во всём этом проекте, через `<script setup>`):

```vue
<template>
  <!-- HTML-разметка. {{ }} — вывод значения, v-if/v-for — условия/циклы -->
  <div>
    <p>{{ count }}</p>
    <button @click="increment">+1</button>
  </div>
</template>

<script setup>
import { ref } from 'vue'

// ref() — реактивная переменная: как только меняется count.value,
// Vue сам обновляет всё, что её использует в <template>, без перезагрузки
const count = ref(0)

function increment() {
  count.value++
}
</script>
```

Ключевые вещи, которые встретятся почти в каждом файле проекта:
- `ref(x)` / `reactive({...})` — реактивные переменные/объекты. Обращение к
  значению `ref` в JS-коде — через `.value`, в `<template>` — без `.value`.
- `computed(() => ...)` — вычисляемое значение, пересчитывается само при
  изменении зависимостей (аналог "формулы" в Excel).
- `defineProps({...})` — объявление входных параметров компонента (то, что
  ему передаёт родитель — например, контроллер через Inertia, см. ниже).
- `v-if`, `v-for`, `v-model` (двусторонняя привязка `<input>` к переменной),
  `@click` (обработчик события) — директивы прямо в HTML-атрибутах.

### 3.4 Inertia.js — клей между Laravel и Vue

Это самая непривычная часть для новичка в этом стеке. Без Inertia пришлось
бы либо (а) писать классический сайт на Blade-шаблонах без интерактивности,
либо (б) делать полноценный отдельный REST/JSON API и SPA на Vue поверх
него, с собственным роутером на фронтенде. **Inertia — способ получить
преимущества SPA (быстрые переходы без перезагрузки, компоненты Vue), не
создавая отдельный API**: контроллер как обычно возвращает данные, но вместо
HTML или сырого JSON — Vue-компонент с этими данными как props.

```php
// Контроллер (backend):
public function index()
{
    return Inertia::render('Addresses/Index', [
        'cityList' => Address::distinct()->pluck('city'),
        // ...
    ]);
}
```

```vue
<!-- resources/js/Pages/Addresses/Index.vue (frontend) -->
<script setup>
defineProps({
  cityList: { type: Array, default: () => [] },
})
</script>
```

Один контроллер-метод = один Vue-файл в `resources/js/Pages/`. Это
однозначное соответствие — если нужно понять, какой файл рисует конкретную
страницу, ищите `Inertia::render('Papka/Name', ...)` в контроллере и
открывайте `resources/js/Pages/Papka/Name.vue`.

Как именно это работает "под капотом" на уровне HTTP-запросов — подробно
разобрано в [REQUEST_LIFECYCLE.md](REQUEST_LIFECYCLE.md). Коротко: при первом
заходе на сайт Inertia отдаёт полноценную HTML-страницу; при клике на ссылку
внутри уже загруженного сайта — тот же самый контроллер вызывается снова, но
Inertia видит специальный заголовок и в этот раз отдаёт не HTML, а чистый
JSON, который фронтенд использует, чтобы подменить компонент без перезагрузки
страницы.

### 3.5 Tailwind CSS

Вместо того чтобы писать `.css`-классы самому (`.card { padding: 1rem; ... }`),
используются готовые utility-классы прямо в HTML/Vue-разметке:

```html
<div class="flex items-center gap-2 px-3 py-1.5 bg-white border border-gray-200 rounded-xl">
```

Каждый класс — одно CSS-свойство: `flex` = `display: flex`, `px-3` =
`padding-left/right: 0.75rem`, `bg-white` = `background: white`, `rounded-xl`
= `border-radius: 0.75rem`. Своего `.css`-файла с классами компонентов в
проекте почти нет — стили всегда рядом с разметкой. Плюс: не нужно искать,
где определён класс, и бояться, что его меняет ещё что-то другое на
странице. Минус, к которому нужно привыкнуть: разметка выглядит "многословно".

### 3.6 Vite — сборка фронтенда

Браузер не умеет исполнять `.vue`-файлы напрямую. Vite — инструмент сборки
(аналог Webpack), который:
1. Компилирует каждый `.vue`-файл в обычный JavaScript.
2. Собирает Tailwind-классы, которые реально используются в проекте, в один
   `.css`-файл (это называется "purge" — ненужные классы не попадают в
   финальный бандл).
3. Склеивает всё в несколько файлов в `public/build/assets/*.js` и `*.css`,
   с хэшами в именах файлов для кэширования браузером (`app-DayBqPTE.js`).
4. Генерирует `public/build/manifest.json` — таблицу "какой логический файл →
   какой физический файл с хэшем", которую читает Blade-директива `@vite(...)`
   в `resources/views/app.blade.php`, чтобы вставить правильные `<script>` и
   `<link>` теги.

**Ключевое правило**: любое изменение файла в `resources/js/` или
`resources/css/` не появится на сайте, пока не выполнена сборка —
`npm run build` (production) или пока не запущен `npm run dev` (режим
разработки с горячей перезагрузкой). Подробности — в
[HOWTO.md](HOWTO.md).

### 3.7 Ziggy — маршруты Laravel в JavaScript

Пакет `tightenco/ziggy` экспортирует все именованные маршруты из
`routes/web.php`/`routes/api.php` в JS, так что во Vue-компонентах можно
писать `route('addresses.store')` вместо того, чтобы хардкодить строку
`/addresses`. Если поменять URL маршрута в `routes/web.php`, но оставить имя
(`->name('addresses.store')`) прежним — весь фронтенд-код с `route(...)`
продолжит работать без изменений.

## 5. Роли и права доступа

Ролей в системе 8, хранятся в таблице `roles`, каждая — набор строк-прав в
JSON-поле `permissions`:

| Роль (`slug`) | Название | Кто это в жизни |
|---|---|---|
| `admin` | Администратор | Полный доступ (`permissions: ["*"]`) |
| `head_support` | Начальник ТП | Настройки, все заявки, отчёты |
| `operator` | Оператор ТП | Приём заявок, адреса, календарь |
| `foreman` | Бригадир | Своя бригада, расписание, утверждение актов |
| `technician` | Монтажник | Свои заявки, акты, комментарии |
| `peo` | ПЭО | Обработка актов (материалы), отчёты |
| `logistics` | Логистика | Обработка актов (списание), отчёты |
| `subscriber_dept` | Абонотдел | Финальная обработка актов, заявки |

Проверка прав — метод `$user->hasPermission('tickets.close')` на модели
`User` (`app/Models/User.php`). Поддерживаются wildcard-права:
`"tickets.*"` покрывает `tickets.view`, `tickets.close` и т.д., `"*"` — вообще
всё. Есть и именованные хелперы-шорткаты: `$user->isAdmin()`,
`$user->isForeman()` и т.д. — они сравнивают `role->slug`, а не проверяют
`permissions`, используются там, где право завязано на роль как таковую (не
на конкретное действие).

Помимо ролей есть **видимость по территориям** — большинство ролей видят
только заявки/адреса/акты своих территорий (`User::territoryScopeIds()` —
объединение территорий бригады пользователя и территорий, назначенных ему
лично). Роли, которым по смыслу положено видеть всё (Оператор, Начальник ТП,
ПЭО, Логистика), получают это не особым кодом, а тем, что им в БД
проставлены вообще все территории.

Два способа авторизации в коде:
1. **Gate** (`app/Providers/AppServiceProvider.php`) — простые булевы
   проверки не привязанные к конкретной записи, например
   `Gate::define('manage-settings', fn($user) => $user->canManageSettings())`.
   Используется в роутах: `Route::middleware('can:manage-settings')->...`.
2. **Policy** (`app/Policies/TicketPolicy.php`, `ActPolicy.php`) — проверки
   привязанные к конкретной записи ("может ли ИМЕННО ЭТОТ пользователь
   изменить ИМЕННО ЭТУ заявку"), вызываются как `$this->authorize('update',
   $ticket)` в контроллере или `$ticket->can('update')` во фронтенд-пропсах.

Многие контроллеры (особенно старые разделы) вместо Policy используют прямые
проверки внутри метода — `abort_unless($condition, 403)`. Это не баг, а
исторически сложившийся стиль; при доработке новых экшенов предпочтителен
Policy/Gate там, где логика нетривиальна.

## 6. Фоновые процессы (что крутится, даже когда никто не смотрит на сайт)

На проде запущены (через **Supervisor** — менеджер процессов, следит, чтобы
они не падали и перезапускались):

| Процесс | Что делает | Конфиг |
|---|---|---|
| `vega8hd-worker` ×2 | Обрабатывает очередь заданий (отправка уведомлений и т.п.) из Redis | `queue:work redis` |
| `vega8hd-scheduler` | Раз в минуту проверяет расписание из `routes/console.php` и запускает то, чему пора | `schedule:work` |

Плюс **root cron** (не Supervisor, обычный `crontab -e`) раз в сутки
запускает скрипты бэкапа БД.

Расписание фоновых задач (`routes/console.php`) — рассылки (утренняя сводка,
вечерний/утренний отчёт — их реальное время срабатывания хранится в
настройках приложения, `SystemSetting`, а не в самом расписании: команда
запускается каждую минуту и сама решает, пора ли ей реально что-то делать),
автозакрытие просроченных заявок, агрегация статистики звонков, отчёты по
сменам.

**Важно**: если поменять код Job/Notification-класса или список задач в
`routes/console.php`, воркер/планировщик не подхватит изменения
автоматически — они держат старый код в памяти долгоживущего PHP-процесса.
Нужен перезапуск через Supervisor. Подробности — в
[HOWTO.md](HOWTO.md#перезапуск-очередей-и-планировщика).

## 7. Инфраструктура сервера

| Слой | Что | Где смотреть |
|---|---|---|
| Веб-сервер | nginx | `/etc/nginx/sites-enabled/*vega8*` |
| PHP | PHP-FPM 8.2, unix-сокет | `/var/run/php/php8.2-fpm.sock` |
| БД | MySQL 8 | `.env` (`DB_*`) |
| Кэш + очереди | Redis | `.env` (`REDIS_*`, `CACHE_DRIVER`, `QUEUE_CONNECTION`) |
| Файлы приложения | — | `/var/www/sites/vega8helpdesk` |
| Логи Laravel | — | `storage/logs/laravel.log` |
| Логи nginx | — | `/var/log/nginx/vega8.ru-{access,error}.log` |
| Процессы (очереди/планировщик) | Supervisor | `/etc/supervisor/conf.d/vega8helpdesk.conf` |
| Бэкапы | root cron | `/root/scripts/*.sh`, `/var/log/backup_helpdesk.log` |

Два разных домена нацелены на одну и ту же файловую систему, но на разные
её части:
- **`vega8.ru`** → `public/` этого Laravel-проекта (основной веб-интерфейс,
  через `index.php`).
- **`app.vega8.ru`** → `mobile/dist/` (собранная статика отдельного
  мобильного PWA-проекта, отдаётся напрямую nginx, без PHP).

Дальше: [REQUEST_LIFECYCLE.md](REQUEST_LIFECYCLE.md) — как именно запрос
проходит через все эти слои.
