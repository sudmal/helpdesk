## 0. Важное про этот проект

**У этого проекта нет отдельного staging/тестового сервера.** Один-
единственный сервер — он же прод. Любое изменение кода, любая пересборка
фронтенда, любая миграция БД — сразу видны реальным пользователям.
Действуйте соответственно: небольшими изменениями, с проверкой каждого шага,
без `migrate:fresh`/`db:wipe`-подобных разрушительных команд без крайней
необходимости и явного бэкапа.

Файлы приложения на сервере: `/var/www/sites/vega8helpdesk`. Владелец файлов
— пользователь `www-data` (тот же, под которым работает nginx/PHP-FPM), а не
тот пользователь, под которым вы заходите по SSH — см. раздел 1.

## 1. Как попасть на сервер

```bash
ssh <ваш_пользователь>@193.233.140.36
cd /var/www/sites/vega8helpdesk
```

Файлы принадлежат `www-data`, поэтому для правки файлов и git-операций
нужно выполнять команды от его имени:

```bash
sudo -u www-data git status
sudo -u www-data php8.2 artisan migrate
```

Для правки самих файлов (не через git) проще редактировать напрямую под
своим пользователем, если у вас есть права записи в эту директорию, либо
через `sudo -u www-data` для команд, которые должны запускаться от лица
веб-сервера (миграции, artisan-команды, `npm run build` — сборка тоже
должна идти от `www-data`, чтобы у собранных файлов были правильные права).

PHP — версия **8.2**, и она не задана как `php` по умолчанию в `$PATH` —
везде используйте явно `php8.2`.

## 2. Частые задачи — куда идти

| Хочу... | Иду в... |
|---|---|
| Поменять текст/подпись на странице, вид формы, добавить кнопку | `resources/js/Pages/<Раздел>/<Файл>.vue` — найти по названию страницы. После правки: `npm run build` (см. [раздел 3](#3-сборка-фронтенда)) |
| Поменять правило валидации, бизнес-логику, что происходит при сохранении | `app/Http/Controllers/<Controller>.php`, метод соответствующего действия. Иногда логика вынесена в `app/Services/*.php` (например `TicketService`, `ActService`) — контроллер тогда просто делегирует туда |
| Добавить новую страницу/раздел | 1) метод в контроллере, возвращающий `Inertia::render('Papka/Name', [...])`; 2) маршрут в `routes/web.php`; 3) файл `resources/js/Pages/Papka/Name.vue` |
| Добавить новое поле в таблицу БД | Новая **миграция** (не правьте старые!), см. [раздел 5](#5-база-данных-миграции) |
| Поменять права роли (кто что может) | Таблица `roles`, поле `permissions` (JSON) — через UI (Настройки → Роли, доступно `admin`/`head_support`) или напрямую в БД. Полный список ролей/прав — в [ARCHITECTURE.md](ARCHITECTURE.md#5-роли-и-права-доступа) |
| Поменять текст уведомления (Telegram/Email/Max) | `app/Notifications/*.php` — класс уведомления. Форматирование текста для Telegram — обычно в `app/Services/TelegramService.php`, для Max — `app/Services/MaxService.php` |
| Поменять расписание фоновых задач (когда что запускается) | `routes/console.php` — после правки нужен перезапуск планировщика, см. [раздел 6](#перезапуск-очередей-и-планировщика) |
| Поменять саму фоновую задачу (что она делает) | Класс в `app/Console/Commands/*.php` — после правки нужен перезапуск планировщика |
| Добавить/поменять JSON-эндпоинт, который дёргает фронт через axios (не целая страница) | Метод контроллера, возвращающий `response()->json([...])` + маршрут в `routes/web.php`. Полный список таких эндпоинтов — в [API.md](API.md) |
| Поменять что-то в мобильном API (для Android/PWA) | `app/Http/Controllers/Api/*.php` + `routes/api.php`. **Обязательно** проверьте и при необходимости обновите `API_MOBILE.md` в корне репозитория — это справочник, которым пользуется Android-разработчик, копия лежит у него отдельно и требует ручной синхронизации (см. `docs/API.md`, раздел "Мобильный API") |
| Поменять права доступа к странице/действию | Middleware в `routes/web.php` (`->middleware('can:manage-settings')`) для простых случаев; `app/Policies/TicketPolicy.php` / `ActPolicy.php` для правил, завязанных на конкретную запись; либо прямая проверка `abort_unless($condition, 403)` внутри метода контроллера (так сделано во многих местах исторически) |
| Поменять общесистемную настройку (рабочие часы, шаг расписания, включить/выключить рассылку) | Раздел "Настройки" на сайте (только `admin`/`head_support`) — хранится в таблице `system_settings` (key-value), читается через `SystemSetting::get('key', 'default')` |
| Поменять стили конкретного элемента | Класс Tailwind прямо в `<template>` соответствующего `.vue`-файла — отдельных `.css`-файлов под конкретные страницы в проекте почти нет |
| Поменять общие для всех форм стили кнопок/полей | `resources/css/app.css`, блок `@layer components` (`.field-label`, `.field-input`, `.btn-primary` и т.д.) |
| Добавить новую роль | Строка в таблицу `roles` (миграция или сеятель) + добавить хелпер `isX()` в `app/Models/User.php`, если нужен именованный шорткат — но чаще достаточно `hasPermission()` |

## 3. Сборка фронтенда

**Любое изменение** в `resources/js/**` или `resources/css/**` не появится
на сайте, пока не пересобран фронтенд:

```bash
cd /var/www/sites/vega8helpdesk
sudo npm run build
```

Это соберёт всё в `public/build/` (JS/CSS с хэшами в именах +
`manifest.json`). После сборки ничего дополнительно чистить не нужно — Blade
директива `@vite(...)` сама читает свежий `manifest.json` при следующем
запросе, а уже открытые вкладки браузера подтянут новую версию
автоматически при следующем переходе внутри сайта (Inertia сама обнаруживает
несовпадение версии ассетов и делает полную перезагрузку — см.
[REQUEST_LIFECYCLE.md](REQUEST_LIFECYCLE.md#b-переход-внутри-уже-загруженного-сайта)).

Команда `npm run build` требует `sudo`, т.к. пишет файлы, которые должны
принадлежать `www-data` (см. раздел 0) — на этом сервере так исторически
настроено, само по себе выполнение `npm` не требует привилегий root.

Локальной среды разработки с горячей перезагрузкой (`npm run dev`) на этом
сервере обычно не поднимают — правки идут сразу "по-боевому" со сборкой
`npm run build` после каждого изменения. Если очень нужно проверить визуально
до полной сборки — можно временно запустить `npm run dev` (Vite dev-сервер с
HMR), но тогда `APP_URL`/доступ к dev-серверу нужно настраивать отдельно;
на практике для мелких правок проще один раз собрать и посмотреть.

## 4. Кэши Laravel — когда чистить

Laravel кэширует конфиг и маршруты для скорости в production
(`config:cache`, `route:cache`). Из-за этого **изменения в `.env`,
`config/*.php` или `routes/*.php` не подействуют**, пока кэш не пересобран:

```bash
sudo -u www-data php8.2 artisan config:clear
sudo -u www-data php8.2 artisan route:clear
# ... внести правки ...
sudo -u www-data php8.2 artisan config:cache
sudo -u www-data php8.2 artisan route:cache
```

Признак, что забыли это сделать: новый маршрут отдаёт 404, хотя в
`routes/web.php` он точно есть, или новая переменная `.env` не читается
кодом.

Если правили только `app/**` (контроллеры, модели, сервисы) — кэш конфига/
маршрутов ни при чём, PHP просто исполняет файл заново при каждом запросе
(в отличие от Node.js-приложений тут нет долгоживущего процесса, который
держит старый код в памяти для обычных веб-запросов — это касается только
воркеров очереди и планировщика, см. [раздел 6](#перезапуск-очередей-и-планировщика)).

## 5. База данных: миграции

Схему БД никогда не правят руками через `ALTER TABLE` в консоли MySQL —
только через миграции, чтобы история изменений была видна в git и
воспроизводима.

Создать новую миграцию:
```bash
sudo -u www-data php8.2 artisan make:migration add_foo_to_tickets_table --table=tickets
```

Это создаст файл в `database/migrations/` с текущей датой-временем в имени
(порядок применения — по имени файла, то есть хронологический). В нём
заполняется метод `up()` (что сделать) и `down()` (как откатить):

```php
public function up(): void
{
    Schema::table('tickets', function (Blueprint $table) {
        $table->string('foo')->nullable()->after('description');
    });
}

public function down(): void
{
    Schema::table('tickets', function (Blueprint $table) {
        $table->dropColumn('foo');
    });
}
```

Применить:
```bash
sudo -u www-data php8.2 artisan migrate
```

**Никогда не правьте уже применённую (старую) миграцию** — Laravel помнит,
какие миграции уже выполнены (таблица `migrations`), повторно она не
запустится, а если кто-то накатит проект с нуля — история разойдётся с
текущей БД на проде. Если нужно поменять уже накаченное поле — новая
миграция, которая его меняет (`Schema::table(...)->change()`).

`php artisan migrate:rollback` откатывает последнюю пачку миграций — на
проде с реальными данными использовать с большой осторожностью (если
`down()` удаляет колонку с данными — данные потеряны).

## Перезапуск очередей и планировщика

Два процесса — обработчик очереди (`vega8hd-worker`) и планировщик
(`vega8hd-scheduler`) — управляются **Supervisor** и работают как
долгоживущие PHP-процессы (см. [ARCHITECTURE.md](ARCHITECTURE.md#6-фоновые-процессы)).
Это значит: если вы поменяли код класса задачи (`app/Jobs/*`,
`app/Notifications/*`, содержимое `routes/console.php`, класс
`app/Console/Commands/*`) — **работающий процесс держит в памяти старую
версию кода** и не подхватит изменения сам.

**После правки кода очереди/расписания — обязательно:**

```bash
# Мягкий способ (только для очереди) — Laravel сам просигналит воркерам
# завершиться после текущей задачи, Supervisor их тут же перезапустит
# заново (autorestart=true), уже со свежим кодом:
sudo -u www-data php8.2 artisan queue:restart

# Или напрямую через Supervisor (нужно для scheduler — для него
# аналога queue:restart нет):
sudo supervisorctl restart vega8hd-worker:*
sudo supervisorctl restart vega8hd-scheduler
```

Проверить статус:
```bash
sudo supervisorctl status
```

## 7. Логи — куда смотреть при поломке

| Что сломалось | Где смотреть |
|---|---|
| Ошибка 500 / исключение PHP | `storage/logs/laravel.log` (последние строки — `tail -100`) |
| Страница не открывается вообще / 502/504 | `/var/log/nginx/vega8.ru-error.log` |
| Медленный/зависший запрос | `/var/log/nginx/vega8.ru-access.log` (время ответа) + `laravel.log` |
| Не приходят уведомления / фоновая задача не сработала | `sudo supervisorctl status` (процесс жив?) → `/var/log/supervisor/vega8hd-worker.log` |
| Ошибка при сборке фронтенда | Вывод самой команды `npm run build` — она печатает ошибку компиляции прямо в консоль |
| PWA (`app.vega8.ru`) не грузится | `/var/log/nginx/app.vega8.ru-error.log` — это отдельный nginx-сервер, статика, PHP тут ни при чём |

## 8. Отладка без tinker

В этом проекте **не установлена команда `artisan tinker`** (интерактивная
PHP REPL-консоль Laravel, которой обычно пользуются для быстрой проверки
кода/данных). Вместо неё — паттерн "одноразовый скрипт":

```bash
cat > /tmp/check_something.php << 'PHPEOF'
<?php
require '/var/www/sites/vega8helpdesk/vendor/autoload.php';
$app = require '/var/www/sites/vega8helpdesk/bootstrap/app.php';
$app->make(Illuminate\Contracts\Console\Kernel::class)->bootstrap();

// дальше — обычный код на Eloquent/фасадах, как будто вы внутри Laravel
$user = App\Models\User::find(1);
echo $user->name . PHP_EOL;
PHPEOF
php8.2 /tmp/check_something.php
rm /tmp/check_something.php
```

Эти строки-бойлерплейт (`require ... autoload.php` + бутстрап ядра)
поднимают полноценное Laravel-приложение внутри обычного PHP-скрипта — после
них доступны все модели, фасады (`DB::`, `Cache::` и т.д.), конфиг. Не
забывайте удалять такие скрипты из `/tmp` после использования (могут
содержать пути/данные, которые не должны надолго оставаться на диске).

Есть готовая artisan-команда `helpdesk:set-password` — если нужно временно
поменять пароль пользователю (например тестовому аккаунту для визуальной
проверки UI):
```bash
sudo -u www-data php8.2 artisan helpdesk:set-password <login>
```

## 9. Полный процесс деплоя

Стандартный порядок для любого нетривиального изменения (backend + frontend):

```bash
cd /var/www/sites/vega8helpdesk

# 1. Внести правки в PHP/Vue-файлы

# 2. Проверить синтаксис PHP (быстрая проверка перед тем, как что-то сломать)
php8.2 -l app/Http/Controllers/ИзменённыйФайл.php

# 3. Пересобрать фронтенд, если менялся resources/js или resources/css
sudo npm run build

# 4. Если менялись .env/config/routes — пересобрать кэш
sudo -u www-data php8.2 artisan route:clear
sudo -u www-data php8.2 artisan config:clear
sudo -u www-data php8.2 artisan route:cache
sudo -u www-data php8.2 artisan config:cache

# 5. Если появилась новая миграция
sudo -u www-data php8.2 artisan migrate

# 6. Если менялся код очереди/уведомлений/расписания
sudo -u www-data php8.2 artisan queue:restart
sudo supervisorctl restart vega8hd-scheduler   # если менялся routes/console.php

# 7. Проверить вживую (открыть страницу/выполнить действие в браузере)

# 8. Закоммитить изменения (файлы принадлежат www-data)
sudo -u www-data git add <изменённые файлы>
sudo -u www-data git commit -m "..."
# git push -- ТОЛЬКО если явно нужно, коммит на проде делается всегда,
# push -- по необходимости (единственный реальный "деплой" тут и есть
# коммит + сборка на самом же проде, отдельного pipeline нет)
```

**Важно про `git add`**: на сервере в рабочей директории всегда есть куча
файлов с изменёнными правами доступа (владелец/режим 644↔755 — артефакт
монтирования через sshfs с Windows-машины разработчика) — они показываются
как "изменённые" в `git status`, но реального содержательного изменения
там нет. Добавляйте в коммит **только конкретные файлы**, которые вы
реально меняли (`git add path/to/file.php`), никогда не `git add -A`/`git
add .` вслепую — иначе в коммит попадёт шум из сотен файлов.

`public/build/` (собранные фронтенд-ассеты) — тоже часть репозитория и
коммитится вместе с исходниками, несмотря на то что обычно собранные файлы
не хранят в git — так исторически заведено в этом проекте, чтобы можно было
откатиться к рабочей версии сайта одним `git checkout` без пересборки.

## 10. Роли и права

Смотреть/менять: раздел **Настройки → Пользователи и роли** на сайте
(нужны права `admin`/`head_support`), либо напрямую в таблице `roles`
(колонка `permissions` — JSON-массив строк, с поддержкой wildcard `tickets.*`
и `*`). Полное описание модели ролей — в
[ARCHITECTURE.md, раздел 5](ARCHITECTURE.md#5-роли-и-права-доступа).

Проверить, что может конкретный пользователь — быстрее всего через
одноразовый скрипт (раздел 8):
```php
$user = App\Models\User::where('login', 'ivanov')->first();
var_dump($user->hasPermission('tickets.close'));
var_dump($user->role->permissions);
```

## 11. Частые грабли

Основано на реальных инцидентах в этом проекте — стоит знать заранее.

- **PowerShell портит PHP/JS-файлы с кириллицей**: если правите файлы через
  PowerShell-команды (`Set-Content`, `>`) с Windows-машины — файл может
  получить BOM (byte order mark) в начале, из-за чего сайт падает с 500
  ("headers already sent"). Правьте файлы напрямую (текстовый редактор с
  UTF-8 без BOM) или через SSH-команды на самом сервере.
- **CRLF в shell-скриптах**: если `.sh`-скрипт создан/отредактирован на
  Windows и потом скопирован на Linux-сервер — переносы строк `\r\n` ломают
  выполнение (`bad interpreter`/непонятные ошибки в середине скрипта). После
  копирования: `sed -i 's/\r$//' script.sh`.
- **Права на файлы после правок через некоторые тулы (sshfs/sed)**:
  файлы могут неожиданно получить права `700` вместо `644` — тогда
  `www-data` (от лица которого работает nginx/PHP-FPM) не может их прочитать,
  сайт падает с "Permission denied". Проверяйте `ls -la` после массовых
  правок, `chmod 644` при необходимости.
- **`vendor/` слетает при `git reset --hard`**: `vendor/` (зависимости
  Composer) в `.gitignore`, но некоторые операции сброса состояния могут
  задеть и его — после `git reset --hard` на всякий случай проверяйте`composer install`, если сайт вдруг перестал открываться с ошибкой про
  отсутствующие классы.
- **Нет tinker** — см. [раздел 8](#8-отладка-без-tinker).
- **Нет staging** — см. [раздел 0](#0-важное-про-этот-проект). Любая
  ошибка видна пользователям сразу.
- **`.env` меняется прямо кодом**: `SettingsController::updateLanbilling()`
  пишет значения LANBilling прямо в файл `.env` на диске через regex-замену
  (не через БД) — если вручную поменяли эти значения в `.env`, а потом кто-то
  сохранит форму LANBilling в Настройках, файл перезапишется снова.
